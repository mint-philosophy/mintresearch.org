Sonnet 5.5’s late refusals reveal how fallback models enter coding scores

Artificial Analysis’s new views show refusals after work has begun and count fallback attempts in the ranked configuration. Its records name Opus 4.8 as Sonnet 5.5’s fallback, while Anthropic’s launch material names Sonnet 5.

The Minty Newsroom · Edited by Codex · 2 October 2026 664 words · ~3 min

Artificial Analysis found that Claude Code usually began working before Sonnet 5.5 refused a coding task. In its October 1 announcement of new refusal-timing and fallback views, the benchmarking firm reported a 4.5% safety-refusal rate for Claude Code with Sonnet 5.5 at maximum effort, against 8.9% for Opus 5.5 at maximum effort. Around 94% of Sonnet’s refusals occurred after the first turn, and the agent then almost always switched to Opus 4.8. The views show both when work stopped on the original model and which model took over.

Artificial Analysis’s methodology defines a safety refusal as a model or provider declining to proceed on safety grounds. It detects provider refusals with fixed rules and model refusals with an AI judge. Its current index averages three benchmarks equally: DeepSWE v1.1, which requires changes to software repositories; Terminal-Bench 4.0, which tests work through a command line; and SWE-Atlas-QnA, which asks technical questions about codebases. Together they contain 303 tasks, each attempted three times. The refusal rate uses the same equal benchmark weighting.

The dashboard’s underlying records, checked October 3, show 45 refusals across Sonnet 5.5’s 909 attempts: 39 on SWE-Atlas-QnA, six on Terminal-Bench and none on DeepSWE. Those raw counts yield 4.95%; equal weighting produces the published 4.5%. Only three refusals occurred at the start. Weighting the later refusals in the same way reproduces the approximately 94% figure. The median recorded refusal turn was 38; 21 occurred at turn 50 or later, with the latest at turn 593.

All 45 refused attempts in that snapshot list Opus 4.8 as the fallback and none as blocked. Completing an attempt does not establish that the task was solved: a completed attempt can fail its verifier and score zero. Under the scoring rules, fallback attempts contribute to the ranked agent configuration’s result. That answers kartik bhardwaj’s question about whether switched attempts count under the original entry. Our calculation puts their maximum possible contribution at 4.5 of Sonnet 5.5’s 68.4 index points; the refusal records do not disclose how many actually passed.

Anthropic names a different fallback. Its September 28 launch announcement says higher-risk cybersecurity work switches from Sonnet 5.5 to Sonnet 5. The system card and help article agree. The Claude Code documentation available October 3 also names Sonnet 5, while assigning Opus 4.8 to cybersecurity fallbacks from Opus 5.5 and Fable models. Artificial Analysis itself reported Sonnet 5 fallbacks in its September 28 Intelligence Index evaluation, affecting about 0.1% of tasks. That evaluation uses a different benchmark mix from the Coding Agent Index.

The coding-agent records identify Claude Code version 2.1.280. The npm registry dates that release to September 22, six days before version 2.1.284, whose changelog added Sonnet 5.5. Anthropic’s current documentation requires 2.1.284 or later for the public model. These version records establish which software Artificial Analysis reports testing, but do not explain its different fallback destination. Artificial Analysis says providers configure safety and fallback behavior and can change it; its figures describe the behavior recorded during benchmarking.

Anthropic’s system card anticipates increased refusals even for benign cybersecurity work. It permits vulnerability discovery in source code but blocks it in compiled binaries, and describes automatic Sonnet 5 fallbacks in its applications. The help article explains why a refusal can occur after work has begun: classifiers check every request and everything the model reads, including files and web results. Material encountered during a task can therefore trigger a switch. That describes the safeguard’s operation, without identifying what triggered any particular benchmark refusal.

In the announcement’s replies, David Larios asked whether judging lower refusal rates as better assumes the tasks should be completed. The benchmark includes security work such as finding and exploiting vulnerabilities. Its refusal records identify the benchmark, turn and fallback, but do not identify each refused task or assess whether the refusal was warranted. The new views let readers distinguish an immediate block from a later switch, while the index score continues to measure the whole agent configuration, including any fallback model.
