LiteLLM’s second compromise distributed credential-stealing malware through its official releases

Maintainers believe developer tokens exposed in AI-tool logs helped attackers redirect releases; independent researchers observed stolen cloud credentials being used to seek model access.

The Minty Newsroom · Edited by Codex · 21 October 2026 799 words · ~4 min

Attackers turned an update to LiteLLM, software used to connect applications to AI providers, into a way to steal credentials from the machines running it. Version 1.107.0 contained both a program that collected secrets and a mechanism for downloading and running further code. Aikido researcher Ilyas Makari confirmed that the malicious Python packages also reached the project’s official Docker image. Users could therefore encounter the same attack while installing the library or deploying the AI gateway as a service. Aikido’s analysis

LiteLLM’s incident notice puts the PyPI exposure window at 11:39–13:23 UTC on October 21, with affected Docker Hub images available until 14:20. Its private enterprise registry was unaffected. The company withdrew the malicious artifacts and advised exposed users to treat their credentials as compromised. Its instructions call for rebuilding affected environments from clean images and rotating exposed credentials; updating the package alone can leave startup malware in place. LiteLLM’s incident notice

The malware did not wait for someone to ask LiteLLM to contact a model. Aikido found files placed where Python would automatically load them when the interpreter started. One component collected information immediately; another could run in the background and periodically seek additional instructions. This made routine use of the affected Python environment dangerous even if the application never explicitly imported LiteLLM. The collection targets included browser passwords, cloud credentials, developer tools and the gateway’s own database of model-provider keys. The attack could therefore expose accounts and services beyond the immediate application. Aikido’s analysis

Upwind’s security research team provided the original public technical report. It found the malicious files in all seven platform-specific Python wheels, while the official Git source tag lacked the payload. The researchers subsequently compared the container contents and build records: the official release machinery had built from an attacker-controlled repository whose name closely resembled the legitimate one. The difference was a hyphen in the GitHub organization name. That finding explained why checking the normal source repository alone would miss the poisoned downloads. Upwind’s report and follow-up

The gateway’s access to other systems widened the possible damage. Upwind identified routines that searched for AI-tool credentials, read accessible process environments and collected cloud service-account credentials. In deployments connected to a LiteLLM database, the malware also sought stored provider credentials. Its separate remote-code loader was dormant at the time of the researchers’ analysis; the credential-stealing component operated independently. The report described capabilities found by examining the package, rather than a count of affected organizations. Upwind’s technical findings

LiteLLM believes attackers obtained three developers’ GitHub CLI tokens from Claude Code responses recorded in its internal deployment’s logs. It says the tokens enabled release changes and approvals; an owner’s token allowed branch protections to be disabled. Publishing permissions had been expanded that week. How attackers first entered the deployment remains unconfirmed. The proposed route is the company’s account of its own setup. LiteLLM’s account of the attack

This was LiteLLM’s second malicious-release incident of the year. On March 24, versions 1.82.7 and 1.82.8 were briefly distributed through PyPI after a compromise involving the Trivy security scanner. The company’s March account identified an unpinned dependency, shared build environments and long-lived publishing credentials available to the compromised process. It brought in Mandiant and Veria Labs, rotated credentials, paused releases and began restructuring its build system. The earlier incident already demonstrated how compromising one dependency could give an attacker access to the machinery that distributes trusted software. LiteLLM’s March account

On March 30, LiteLLM announced that its revised release system was live. It separated validation and publishing into different repositories, isolated test and security-scanning environments, adopted PyPI Trusted Publishing and began signing Docker images. These controls addressed the ways an attacker might steal publishing secrets or replace an artifact after release. The October investigation describes an attacker using developer privileges to make the legitimate machinery build and distribute malicious material. A valid signature can identify the system that produced an image while leaving the security of that system’s inputs and permissions unresolved. LiteLLM’s release-system announcement

Wiz researchers Benjamin Read and Rami McCarthy then reported downstream use of stolen credentials. Between 16:20 and 17:01 UTC on October 21, they observed attackers testing AWS role credentials taken from build runners and Kubernetes nodes in several environments, followed by requests listing available AI models. Wiz described this as consistent with stealing access to paid inference services. In a smaller number of environments, it also saw broader account and permission discovery. The observations show attackers using stolen access within hours of collection, even after the malicious software had been removed from distribution. Wiz’s observed activity

Wiz also judged the malware’s coding patterns consistent with AI-assisted development. That assessment is an inference from the code. The observed release compromise and use of stolen credentials do not establish that an AI agent conducted the intrusion. Wiz’s analysis
