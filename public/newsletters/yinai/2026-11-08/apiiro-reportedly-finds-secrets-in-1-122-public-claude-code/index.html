Apiiro finds credential strings in 1,122 public Claude Code settings files

Permanent command approvals can save embedded passwords in project files that later reach GitHub. Anthropic’s Boris Cherny acknowledged the missing secret scrubbing and discussed possible fixes.

The Minty Newsroom · Edited by Codex · 8 November 2026 986 words · ~5 min

Apiiro researchers Shmulik Cohen and Matan Giladi reported on November 5 that Claude Code’s saved permission rules contained credential strings in 1,122 public GitHub files. Their investigation follows a password from a local configuration file into a command, then into a permanent approval rule, and finally into a published repository. In the subsequent Hacker News discussion, mirrored by HN Companion, Anthropic’s Boris Cherny acknowledged that Claude Code historically lacked secret scrubbing and said the team would prototype prevention measures.

Claude Code can save an approved shell command in .claude/settings.local.json when a developer chooses “Yes, and don’t ask again.” Anthropic’s permissions documentation says a rule without a wildcard matches one exact command. If the command includes a database password or API token copied from local configuration, that credential can become part of the saved rule. Apiiro reproduced the behaviour with Opus 5.5 and Fable 5.1. Its documentation comparison of 16 coding agents identified Claude Code as the only one it could confirm writes the full approved command to a project file by default.

Anthropic’s settings documentation describes a safeguard: when Claude Code first writes the file inside a Git repository, it adds an entry to the user’s global Git excludes file. That protection does not travel with the project in its own .gitignore. Apiiro identifies exposure routes through a copied project on a machine or container lacking the global exclusion, a folder that becomes a repository later, or a file already tracked by Git. In the Hacker News exchange, Cohen withdrew his initial suggestion that a fresh clone alone would cause the problem. In 539 of 1,105 examined repositories, a Claude-co-authored commit changed the settings file; as iTWire noted, that does not establish that those commits introduced each credential.

Apiiro searched GitHub between November 1 and 3, dividing searches by file size to work around the search result cap. It found 104,185 public copies of the local settings file and classified 1,122, about 1.1%, as containing credentials. Its rules looked for known provider key formats and passwords or tokens paired with public hosts; a language-model reviewer examined masked values, and a candidate counted only when the rules and review agreed. Apiiro did not use or test the credentials. One organization it notified confirmed that its key had been live.

The classified files contained 1,379 distinct credential strings, including database passwords and Supabase service-role keys. Larger files were more likely to contain them: about one in ten files over 8 KB, compared with fewer than one in 500 under 500 bytes. Adding Git history, shared settings and other agent files brought Apiiro’s total to 2,539 distinct strings across 1,994 repositories. The historical search found credentials absent from current copies, showing why deleting a file does not remove everything previously published.

Apiiro also ran Gitleaks and TruffleHog over the files. Both missed 215 of the 1,122 files it classified as containing credentials. The researchers attribute much of the gap to ordinary passwords inside commands, such as values following PGPASSWORD=, which lack the distinctive prefixes or formats of provider-issued keys. They argue that the predictable local file path also makes these records useful to credential-stealing malware. Their examples include the September 2025 Shai-Hulud worm, which used TruffleHog to search victims’ files, and the earlier Nx package compromise, which tried to enlist AI command-line tools to search for credentials.

Users had reported the mechanism well before Apiiro’s scan. GitHub issue #5544, filed in August 2025, described plaintext credentials in approved commands; #11982 that November reported the missing project ignore entry. In #13106, filed that December, a user described discovering tokens in a committed settings file after receiving a security alert. Automation closed all three without a staff response. Apiiro also credits ironPeak’s February investigation and scanning tool, and cites Lakera’s April finding of credentials in 33 such files across 30 published npm packages.

Broader GitHub research gives those findings context. Michael Meli, Matthew McNiece and Bradley Reaves’ NDSS 2019 paper “How Bad Can It Git?” found leaks in more than 100,000 repositories using distinctive credential formats. GitGuardian’s 2026 report found secrets in 3.2% of Claude Code-assisted public commits against a 1.5% baseline, while cautioning against attributing the difference simply to tool failure. Apiiro’s investigation documents a specific way an approval system can create a file containing credentials.

Cherny, introducing himself as part of the Claude Code team, responded on November 7. He argued that automatic Git exclusion meant the exposed files had been manually created and committed, recommended host-side secret scanning, and urged users to switch to auto mode, where a classifier reviews commands. When the commenter bluebands observed that auto mode still asks about sensitive commands and can save a permanent approval, Cherny replied, “Yeah good catch.” His proposed experiments included improving auto-mode detection and adding basic secret scanning; the exchange did not announce a shipped fix.

Commenters also debated Cherny’s comparison of auto mode with manual review. Anthropic’s August article reported that, in a study of 1,053 paid testers, people caught 13.6% of planted dangerous commands while auto mode blocked 89%. RossBencina linked Zimo Ji and colleagues’ arXiv paper “Measuring the Permission Gate: A Stress-Test Evaluation of Claude Code’s Auto Mode”. On 128 ambiguous DevOps tasks, the researchers reported that 81% of dangerous actions went unblocked; some actions were project-file edits outside the classifier’s scope. That evaluation tests permission enforcement under a different task design, and does not measure how often approval files retain secrets.

Apiiro recommends referencing credentials through variables such as $DB_URL, so the saved command contains the variable name, and using appropriate command patterns instead of approvals containing literal passwords. It advises rotating exposed credentials before cleaning up files and repository history. The researchers notified affected organizations on November 2 and 3 and Anthropic before publication; their November 8 update incorporated Cherny’s response. His comments left the choice and timing of a product change open.
